> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or

> `2026-11-16-m3-window-c.state.md` first. The user requested implementation in a fresh Codex

**Goal:** evaluate the existing retrieval baseline against historical coded faults in an
operator-run, isolated window, releasing only aggregate metrics.

**Architecture:** add a temporal real-corpus wrapper around the existing retrieval and scoring
functions. A separate sealed entry point migrates and builds a disposable database, then writes
a strictly numeric report. Window C supplies Postgres on tmpfs in a network-isolated pod.

**Tech Stack:** existing Python 3.12, psycopg, pgvector, German `de_tech`, e5-large, pytest,
Docker locally and Podman on the box; no new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-11-m3-hybrid-retrieval-design.md`, sections 3–4,
with the implemented M3 amendments in `2026-11-05-m3-retrieval-on-dev3-standin.md`.

## Global constraints

- No agent reads, lists, searches, or runs a command against client-data roots, including to
  export an aggregate. Every real-data command is operator-only, outside Codex.
- Raw export immutable; all rows indexed, no solution/status/year exclusions added.
- Use existing `index.build`, `retrieve.search`, `eval.score`, and `eval.query_text`.
- Stored vectors retain `passage: `; default query prefix is `query: `; RRF k=60, pools=100.
- Labels stay in `eval_label`; retrieval SQL cannot consult it.
- No real per-group, per-query, ticket-id, error-code, date, text, serial, or path output.
- A numeric leaf type alone is insufficient: report values must be derived counts/metrics,
  never numeric ticket IDs or codes. Validate the exact schema before writing or releasing.
- All new outputs/logs from code that can see real rows use `recall.sealed`. Do not alter that
  helper, existing guards, registrations, policy files, or the airlock marker.
- Only the existing `tools/guard/export_aggregate.py eval_real` releases the numeric report.
  Do not modify that gate to accept strings or additional content.
- Airlock open/close, SSH/box runs, human review, cleanup verification, and release are the
  operator's steps. No `git push`; publication is only through `make publish`.
- If a test looks wrong, stop and report it; do not rewrite it to make the implementation pass.

## Review focus

1. Month-end/leap-year cutoffs and exact-boundary tickets must obey one calendar rule.
2. A query with no older same-code ticket is counted, not silently removed or scored as zero.
3. Missing dates/codes and empty corpora must produce honest coverage, never fabricated scores.
4. Every retrieval variant must exclude holdout/future tickets in SQL; reranking cannot fix leakage.
5. Failure, cancellation, stale reports, PostgreSQL logs, and anonymous volumes must not retain
   real text outside the sealed mount or disposable tmpfs database.

## Decisions for operator review

These details make the existing spec executable; they are proposals, not new approved policy.

- Calendar rule: let `latest` be the maximum non-null indexed creation date. Subtract six
  calendar months, clamping the day to the target month's last day. Queries are labeled tickets
  with `cutoff <= created <= latest`; candidates have `created < cutoff`. Missing-date tickets
  stay indexed and count toward coverage, but enter neither side. No valid date means no queries.
- Keep all six existing `eval.VARIANTS` and all three `QUERY_MODES` for comparability. Fix k=10
  for this first real report. Do not expose arbitrary keys, per-group output, or label inputs.
- Use the exact normalized code string already produced by `index.normalise_code`. A ticket
  with multiple codes remains one composite label; do not quietly change relevance to code
  overlap. Same code is a proxy for same problem, not proof of the same successful solution.
- Keep empty-solution candidates as the approved M3 baseline requires. This does not measure
  whether a technician receives a usable fix. Report that limitation with the results.
- Dense pool (decided 2026-11-23 after review): HNSW returns `hnsw.ef_search` rows (default
  40) before the date filter applies. `run_real` therefore sets `hnsw.ef_search` to
  `retrieve.POOL` and `hnsw.iterative_scan = strict_order` on its own connection only;
  `retrieve.search` and its defaults are unchanged. Whether the stand-in runs E13–E16 used
  HNSW (and so a dense pool of at most 40) is unverified and stays an open question.
- Reuse `score` unchanged: group-macro metrics, recall denominator `min(10, |relevant|)`.
  Its `mrr` observes only the retrieved top 10 in this plan; describe it as MRR@10 when interpreting.
- Frozen report shape below. The explanation of coded-fault bias stays in documentation;
  the report marks it with `coded_faults_only: true`, not a free-text caveat.

### Report v1

Exact top-level keys: `schema_version` (=1), `k` (=10), `holdout_months` (=6),
`coded_faults_only` (=true), `embedder_is_a_model`, `n_tickets`, `n_dated_tickets`,
`n_labeled_tickets`, `n_query_tickets`, `n_candidate_tickets`, `modes`.

`n_labeled_tickets` counts non-null code labels across the whole indexed corpus;
`n_query_tickets` counts labeled, dated holdout tickets, including unscorable queries;
`n_candidate_tickets` counts every dated pre-cutoff ticket, including unlabeled candidates.
Label coverage is `n_labeled_tickets / n_tickets` when the denominator is nonzero.
`embedder_is_a_model` is false for the hashing stand-in and true only for the pinned e5 model.
Store neither model identity nor provenance strings in the released document; the operator
records code/image/model pins separately from client-derived output before the window.

`modes` has exactly `full`, `title`, `head`. Each has exactly the six current variant names:
`dense_passage`, `dense_query`, `lexical`, `fused`, `fused_query`, `fused_dense2`.
Each entry has exactly the existing score keys: `k`, `n_queries`, `n_unscored`, `n_groups`,
`recall_at_10`, `mrr`, `ndcg_at_10`. No scorable queries means null metric values.
All leaf values are finite numbers, booleans, or null. No dynamic group keys or list of queries.

Counts are nonnegative integers (booleans are not integers for validation). Metrics are null
or finite numbers in [0, 1]. Pin the constants and the expected variant/mode names; extra keys,
missing keys, arbitrary numeric payloads and inconsistent counts are refused. For each cell,
`n_queries + n_unscored == n_query_tickets` and `n_groups <= n_queries`; null metrics occur
exactly when `n_queries == 0`. No hard-coded quality threshold applies to a synthetic run.

Use `recall/window-c:pinned` with baked-in, revision-pinned e5 weights and
`recall/postgres:18`. Create `infra/eval/Dockerfile.window-c` using the eval image's locked
dependency/PYTHONPATH setup and the profiler image's pinned e5 download/offline load check.
Copy only `src/`, `profiler/`, `insight/`, `pyproject.toml` and `uv.lock`; no catalog or tests.
The existing profiler Dockerfile imports catalog modules absent from the publication allowlist;
reusing it from a published checkout would fail. The M4 eval image requires a separate weights
mount. The dedicated C image avoids both dependencies without changing either existing image.
Record immutable image IDs and code/model revisions in operator preflight evidence; run those
exact local images with pulling disabled. Build on a clean published checkout on the box,
never from a workstation context that could contain client files. Ship/build both images
before staging; neither build nor dependency resolution occurs inside the window.

The CLI uses the fixed disposable DSN
`postgresql://recall:recall_dev_only@127.0.0.1:5432/recall` and requires
`RECALL_WINDOW_C=1`. It never imports `recall.config.settings`, reads `.env`, accepts a DSN flag,
or honors `PG_DSN`/`RECALL_PG_DSN`. The window supplies that sentinel inside its isolated namespace.

`eval_real.json.tmp`, and `window_c.log`. The only input mount is the sealed quarantine mount;
model weights remain baked in the image. Do not mount the repository, host home, or Docker socket.
Worker root is read-only with writable tmpfs for temporary runtime files; PostgreSQL's data,
WAL and temporary relation files all live under its tmpfs mount. Verify the host's tmpfs/swap
arrangement meets the existing no-disk requirement before staging; tmpfs alone is not proof.
